## 与 94MB 基线对比

- **MB 粒度:持平(94M ↔ 94M)**
- **归因**:v0.0.10 全部改动为代码层重构,零资产/DLL/字体变更:
  - B2 `List.unmodifiableOf` — API 别名迁移,纯代码
  - B3 缩略图磁盘清理迁 `Isolate.run` — 纯代码逻辑
  - B4 Win32 FFI 迁 `@Native assetId` — 绑定层迁移,不影响产物体积
  - B5/B7 网络路径 scheme 统一 + 失败诊断 — 纯代码逻辑
  - B6 Pub Workspace — 无代码变更(实测结论文档)
- 故体积零变化符合预期。FFI 迁移(@Native assetId)不改变产物体积:
  绑定仍链接同一批系统库,仅声明方式从 `lookupFunction` 运行时查表
  改为 `@Native` 编译期解析,二进制体积差异在 KB 级以下,不改变 MB 粒度。

## 剩余杠杆声明

### (a) `--obfuscate` 不启用

**不采用**,与"出错可定位"里程碑核心价值直接冲突。本里程碑
(v0.0.10)的核心价值是**出错可定位**:任何错误发生时,无需接调试器
即可知道错误在哪个文件哪一行、调用链是什么(见 `.claude/CLAUDE.md`
项目描述)。`--obfuscate` 会抹除栈符号,错误堆栈变为 `a.b.c` 形态,
文件名+行号定位能力被直接破坏——这与里程碑目标根本对立,故不采用。
(代价:app.so 保留完整符号,体积未压缩;可接受。)

### (b) mpv DLL — media_kit 红线

`libmpv-2.dll`(29.7MB)是 Release 目录最大单项,但来自
`media_kit_libs_windows_video` 预编译二进制。**media_kit 不可改动**
是项目红线(用户钦定 memory: project_media_kit_immutable):只处理
项目封装/UI/测试层,绝不修改 media_kit 基础能力。故 mpv DLL 体积
不在可优化范围。

### (c) 字体治理 — v0.0.9 已完成

字体目录 31.6MB(三静态死重)→ 17.8MB(可变字体单文件)已在
v0.0.9 落地(commit a71ca714),-44%。本轮确认仍为 17.8MB 可变字体,
**v0.0.10 无新字体杠杆**。剩余字体侧候选(见 v0.0.9_baseline.md
§"低收益候选"):empty_state w200→w300 + 3 档静态可省 ~4.4MB,但需
视觉验收且可变→静态切换无净收益除非减档,搁置。

## 结论

**v0.0.10 体积与 94MB 基线持平(94M),符合预期。** 本里程碑全部
改动为代码层重构(Dart 3.13 定向采纳 + 网络路径修复),零资产/DLL/
字体变更,体积零变化是正确结果。字体 17.8MB 可变字体(v0.0.9 成果)
确认仍在位;剩余杠杆(--obfuscate / mpv DLL / 字体减档)均因红线或
里程碑核心价值冲突而不采用。体积趋势:稳定,无回归。
